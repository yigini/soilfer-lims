Claude responded: You're right.
You’re right. Cleaning up once won’t stop it filling again.
Why it fills. Each startup test copies the whole production database, plus its files, several times, which takes about 32 GB per test. When a test ends, those copies stay on the server, and so do old app images and the build cache. We’ve run many tests in two days, and their leftovers are most of the 26.6 GB that can’t be removed today.
What would stop it, with one approval from you instead of one per cleanup:
1. A standing cleanup rule after each test. Once a test has ended and its evidence is saved in Git and checked, Pip deletes that test’s working copies of the database. The small evidence files stay. This is the big one.
2. A size cap on the Docker build cache. For example 5 GB, so it trims itself instead of growing.
3. A cap on old app images. Keep the running one, the one before it and the one being tested; Pip lists anything older for you once a month.
4. A space check before every test. If space is short, the test doesn’t start and you hear about it early, not halfway through.
5. Old backups. Copy them off the server to Google Drive on a schedule, and keep only the recent ones on the server.
Your data stays safe under this: the production database, its recent backups and anything without a verified copy are never touched by the rule.
Shall I write this up as a rule for Pip on #162? You’d approve it once, and I’d check each cleanup report against it.
