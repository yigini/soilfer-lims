LIMS Build Spec

Every open finding from Volumes I through IX, consolidated into 34 sequenced work packages with exact file paths, acceptance criteria and dependencies. Written to be executed by a coding agent rather than read as a strategy document.

Packages
34 · 6 stages
Baseline
416c201 + uncommitted tree
Estimate
~9 weeks single developer
Hard rule
Stage 0 before anything else

Read this first. Four times in this codebase, correct code has been written and never called: checkScope, validateSampleMatrix, a "catalogue" that was a display-name lookup, and workflowContract's validators. Each was good work that reached nothing. The cause is that no test can run — server/tests/setup.js does not exist, so eleven suites fail at import and CI does not exist to notice.

Therefore Stage 0 is not optional and not reorderable. An agent executing this spec must complete WP-01 through WP-03 and see them pass before touching any other package. Every later package specifies a test as part of its acceptance criteria, and those tests are the only thing preventing a fifth instance of the pattern.

Priorities: P0 produces wrong output or lost work today · P1 integrity or compliance · P2 correctness and consistency · P3 productisation and future obligations.

Guardrails — constraints on the executing agent

  • Do not run anything against production. All work is local. Deployment is a human decision. lims.yigini.net is live with seven laboratories' data.
  • Do not seed a catalogue over existing rows. Laboratories have hand-created analyses with free-text units. WP-17 specifies a match-and-confirm migration, not an overwrite.
  • Do not change interpretation band values. The thresholds in interpretationService.js were verified correct in Volume VIII. Packages here change unit handling and coverage, never the numbers.
  • Do not delete the glosis_* columns until WP-32, which migrates them to a side table first.
  • Do not add Puppeteer. The working tree already chose pdfkit; that decision stands.
  • Commit per work package, referencing the WP id. Do not batch multiple packages into one commit.
  • If a package's acceptance criteria cannot be met, stop and report. Do not substitute a partial implementation and mark it complete — that is precisely how the four dead-code instances arose.
