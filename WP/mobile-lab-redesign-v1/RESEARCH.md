# Platform research and design implications

Official sources reviewed 8 September 2026. Recheck current support and native toolchain requirements during implementation. These sources support platform behavior; the laboratory policies in this package are design proposals requiring validation against the lab's SOPs.

| Source | Relevant finding | Decision for SoilFER |
|---|---|---|
| [web.dev — PWA installation](https://web.dev/learn/pwa/installation) | Installation and install UI differ by browser and platform. | Provide platform-aware installation help, manifest, icons and standalone routing. Do not show a nonfunctional universal install button. |
| [WebKit — Safari 26 announcement](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/) | iOS 26 Add to Home Screen can open sites as web apps by default, with user control. | The missing current manifest does not mean iOS cannot create a home-screen app. It still needs deliberate identity, assets, routing and offline implementation. |
| [WebKit — storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/) | Web storage is normally best effort; quota, persistence decisions and eviction depend on browser conditions. | Check `estimate()` and request persistence where supported. Explain denied persistence and storage pressure; a successful request is not a universal data-loss guarantee. |
| [WebKit — origin private file system](https://webkit.org/blog/12257/the-file-system-access-api-with-origin-private-file-system/) | Origin-private files remain browser-managed storage. | OPFS may help large files where supported, but is not an escape from browser storage lifecycle risks. |
| [MDN — Background Synchronization](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API) | The API has limited cross-browser availability and needs a secure context. | Foreground, resume and manual synchronization must work independently. Do not promise closed-app upload on every iPhone. |
| [MDN — offline and background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation) | Offline caching and background tasks require explicit lifecycle handling. | Cache the application shell and selected work resources; keep authoritative writes in a durable command outbox and handle suspension. |
| [Capacitor — platform](https://capacitorjs.com/) | A web application can share a native runtime across Android and iOS. | A candidate for reusing React UI and domain logic while providing packaged mobile applications. This is an architecture recommendation, not a selected/licensed dependency yet. |
| [Capacitor — storage](https://capacitorjs.com/docs/guides/storage) | Web storage inside a WebView can be transient; Preferences is for small values. Database solutions require a deliberate choice. | Use a vetted SQLite/private-file adapter for production offline native work, with encryption/key handling and maintained plugins. A wrapper alone does not provide durable laboratory storage. |
| [Capacitor — development environment](https://capacitorjs.com/docs/getting-started/environment-setup) | Native platforms have their own build tools; iOS development requires the Apple toolchain. | Keep Windows-based web work moving, and plan a Mac/Xcode or approved macOS CI path with organizational signing for iOS. Verify current versions when implementation starts. |
| [MDN — VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) | The visible viewport can change independently, including with the on-screen keyboard. | Test visible input and action positioning; avoid rigid `100vh` forms and keyboard-covered fixed footers. |
| [MDN — getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) | Camera access requires permissions and secure context; failures have distinct causes. | Start scanning intentionally; handle denied permission and camera lifecycle; keep manual/HID entry available. |
| [W3C — target size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | WCAG 2.2 AA defines a 24 CSS-pixel target minimum with exceptions/spacing provisions. | Choose larger 44–48px targets for practical laboratory touch use. | [W3C — reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) | Content should reflow at small widths, with exceptions for content inherently requiring two dimensions. | Phone views prioritize tasks and linear relationships; retain bounded detailed maps/worksheets where needed with accessible alternatives. |
| [W3C — WCAG 2.2 additions](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/) | Focus visibility, alternatives to dragging and target sizing need attention. | Test keyboard/screen-reader focus and provide tap/button alternatives for maps, drawers and batch reordering. |

The work queue and server receipts must remain authoritative without push. |

## What follows from the research

The recommendation combines adaptive React views, an installable web application, and native Android/iOS packages for sustained offline laboratory work. Native storage can improve durability and device integration when correctly implemented; it cannot protect unsynchronized work from device loss, app deletion or every hardware failure. Recovery and device management remain operational responsibilities.

Full offline capture and immediate global authority are different capabilities. A disconnected device cannot know about a new server-side reassignment, revocation, amendment or calibration withdrawal. Versioned work packs, bounded offline authorization, local provisional status and conflict resolution address this limitation. Final release should require a fresh online validation step; this is a recommended laboratory control, not a browser requirement.

No claim is made that a specific native plugin, every handset, arbitrary connected instrument, or every browser already supports these requirements. Validate the chosen stack and lab hardware with the test matrix before advertising support.
