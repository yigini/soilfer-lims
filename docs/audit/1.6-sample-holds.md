# Sample holds and retained intake cancellation — audit 1.6 (WIP)

#183 starts from merged/deployed #178 and #179. Scope is pinned by comments 5993636692, 6005420704 and the superseding association pin 6005660537. The #179 migration SQL, loader and installer remain unchanged. This branch is independent of the unaudited #182 branch.

Implemented checkpoint:

- Additive SampleHold table with hold/attribution/compatibility checks, open-hold index, and one-backfilled-hold-per-sample partial unique index. Four nullable WorkItem cancellation provenance columns; no old row rewrite or back-fill yet.
- Canonical JS/SQL held rules include open rows and legacy markers/mirrors, and fail closed. Manager resolution is transactional/audited, preserves every marker field, appends resolutions, and clears compatibility markers only after the last bound hold resolves. New LIVE holds preserve previous resolution history.
- Named intake undo/rejection cancellation actions retain eligible work and record cancellation provenance. Generic cancellation/reactivation cannot supply the private action capability. Recorded results, scans, evidence events, attempts, drafts and sealed states block the entire sample operation with zero writes.
- Legal sample re-acceptance reuses known intake-cancelled rows, keeps their cancellation history, clears assignment/timestamps, leaves dropped analyses cancelled and refuses legacy cancelled keys. A scanner canary confines this helper to the central sample acceptance transaction.
- Acceptance and central assignment block held samples; assignment only admits ACCEPTED/PROCESSING. Intake preparation/commit use the canonical hold rule. Undo no longer removes WorkItems.
- Sample marker updates use a narrow central compatibility writer, preserving raw legacy lifecycle values. The scanner confines its callers to the hold service.

Checkpoint validation on an owned schema/seed database (never the working laboratory DB): 3 suites / 108 tests pass, including the existing source inventory. Refusals and audit failures compare checksums/counts of every table. Migration was applied only to an empty private template with zero Sample/WorkItem/Result/AuditLog rows; integrity_check is ok. No production migration or deployment.
