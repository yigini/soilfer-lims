# Intake integrity migrations

Run `node server/scripts/workitem_duplicates.js --database <existing SQLite file>` before release. The default is read-only and works before the new column exists. Record the group count in the release receipt. Stop the release if any group exists; never choose a canonical item automatically.

For an installation with duplicates, back up the database and stop all writers. Apply only `20261004190000_add_workitem_duplicate_marker` first. A manager must review each group, including `HAS_RESULTS` warnings, and explicitly resolve it:

```text
node server/scripts/workitem_duplicates.js --database <existing file> --resolve --sample <sample ID> --analysis <analysis code> --keep <WorkItem ID> --reason "Manager's reason" --actor <manager username>
```

The command marks the other active items with `duplicateOf`, records one audit row for each changed item, and preserves all results, submissions, batches and history. It refuses stale groups and invalid kept IDs. Re-run the read-only listing; continue only at zero groups. The next migration installs the partial unique index. Duplicate groups cause index creation to fail, leaving the index migration unapplied. The marker migration is independently additive so managers can resolve existing duplicates before the constraint is installed.

The consignment migration only adds nullable `declaredExpectedCount`, checked as NULL or at least 1. The compatibility `expectedCount` column and every existing default, column position, index, FK and stored value remain unchanged. All new application/display reads use the declaration; NULL means not declared. New rows also write the compatibility count (declared value, otherwise received count) so v1.7.0 can read them after an image rollback.

Before adding the column, save `node server/scripts/backfill_consignment_counts.js --database <existing file>` output as the legacy dry-run plan. It records the old rows, positive/NULL split and `(id, code, expectedCount)` fingerprint. In the release's same transaction, add the column and call `applyPlan(db, savedPlan, { inTransaction: true })`: positive old counts are copied exactly; zero/negative old counts leave the new column NULL. No historical code/count is changed and no intention is inferred. Roll back schema and back-fill together on any failure. The repeat reports zero changes; only the original saved IDs are eligible, so a later unknown declaration is never back-filled from its compatibility received count.

Run `node server/scripts/consignment_schema.js --database <existing file>` before and after for streamed read-only tuple/schema receipts. Counts/fingerprints, existing definitions, all child links and FK enforcement must stay equal. Keep FK enforcement ON throughout: there is no table rebuild or alternate SQL variant. The standalone back-fill accepts `--apply --plan <original plan>` after migration; default mode is read-only, and a post-migration dry-run requires the saved pre-migration plan. Conflicting or stale values are refused rather than overwritten.

Known production drift, preserved here and deferred to 8.1: `Consignment.updatedAt` has `DEFAULT CURRENT_TIMESTAMP`, and its custody columns were appended after `updatedAt`. The generated Prisma schema orders those columns differently and has no updatedAt default. The additive migration supports both without changing either definition. `expectedCount` is deprecated for later removal in 8.1.

The request-only adapter accepts old `consignment.expectedCount` as an alias for `declaredExpectedCount`; conflicting fields return 422 before writes. The client sends the new field. Intake/list/detail responses include the declaration and keep the legacy response key as the same declared value, including NULL for not declared. The stored rollback-compatibility count is never exposed as a declaration. This is an explicit response-nullability change in scope comment 5984099200.

Marked duplicates are excluded only from canonical per-analysis lookup and work/gate generation. Publication completeness, review atomicity, result invalidation, QC disposition, retention and other safety checks continue to inspect every row. Managers must waive unworked duplicates through the existing reasoned, audited path; marking a duplicate never makes unfinished work publishable. The test database installs the actual partial index even when its schema was initialized with Prisma db push.

Scope decisions on #178 preserve the two-step arrival boundary: no lab sample code, WorkItem or order at physical arrival; final acceptance rechecks current facts. Zero grams is a valid observation and stays zero. Mass uses implicit grams (or explicit `g`); other units are refused without conversion. Configurable required custody fields are deferred to chain-of-custody policy work. Checklist configuration, the general sample state machine and repeat WorkAttempts remain outside this issue. Only the additive declaration receives the reviewed legacy copy; no existing sample/code/count is overwritten. Duplicate resolution occurs only for explicitly reviewed groups.
