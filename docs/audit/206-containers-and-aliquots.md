# #206: physical containers and aliquots

Container creation records physical material, not an analytical result. A bulk container can be followed by fine earth, ground material, an aliquot or an archive container. Derived containers require an existing active parent from the same sample. Identity, parentage, creator, creation time and mass are append-only. Creation and listing use the sample's authoritative laboratory/project scope; creation additionally requires `MANAGE_CONTAINERS` and a named actor. Closed samples and active holds refuse creation.

The sample detail work panel shows the hierarchy, optional masses and linked attempts. Labels identify the container kind, issued code and parent sample. QR generation is local and encodes the issued container code. All labels and policy descriptions are provided in English, Spanish, Latin American Spanish, French and Portuguese.

`container.codeFormat` and `container.sequenceReset` are LAB policies in the registry. The default format is `C-{LAB}-{YY}-{SEQ:6}{CHK}`. The existing format/check-character implementation computes the checksum over the complete code. The separate additive `ContainerSequence` table uses the same transactional UPDATE/RETURNING allocator pattern as `LabSequence`; it does not consume sample numbers or change historical numbering DDL. Both allocators reserve existing container codes and sample aliases. Failed transactions return their counter increments.

`WorkAttempt.aliquotId` remains the existing nullable column. New execution INSERTs and repeat reservations may link an active ALIQUOT from the same sample. An additive INSERT trigger also enforces that rule against direct writes. Every existing #190/#191 guard remains unchanged: a reserved repeat keeps its link during first fill, and recorded attempts cannot acquire or change a link. No historical links are inferred or backfilled. Workbench selection rides with the existing draft `values` object until Record; drafts do not create attempts. A repeat that needs a different physical aliquot must choose it when the repeat is requested.

The reviewed #206 installer adds `SampleContainer`, `ContainerSequence`, indexes, four guards and one `_schema_migrations` receipt. Its source digest is pinned. Read-only preflight refuses partial, changed or populated unmarked storage and invalid receipts. APPLY verifies all pre-existing table columns/rows before and after the transaction, records zero backfilled rows and verifies integrity/foreign keys. Repeated application returns NO_OP with zero changes. Fresh Prisma initialization may supply an empty container table; the installer adds only its independent counter and guards. The counter is deliberately installer-owned because Prisma cannot express its CHECK constraints.

The default entrypoint runs this installer after the #200 prerequisite and before application startup/jobs. Startup requires the exact complete receipt and guard definitions. This source is a new backlog change; it grants no authority to replay any completed release, proof, build, installer attempt or gate. Deployment requires an exact-head Claudio audit PASS and a separately reviewed fresh forward-release kit/gate.

Storage locations/movements remain #207, and consumption, disposal and retention transitions remain #208. #206 exposes no update/delete/lifecycle endpoint; those issues must supply reviewed successor guards. A detached test fixture simulates a future disposed aliquot and verifies that recorded attempts retain their original linkage while new links are refused.
