# Result writes and attempt links — audit 1.5

Issue #182 and scope pin https://github.com/yigini/soilfer-lims/issues/182#issuecomment-6003803971 govern this change.

`resultWriteService` owns all Result creation and WorkItem.result cache updates. Runtime callers use the caller's transaction, fresh sample/work item/method/equipment reads, the laboratory number policy and shared number parser. Scientific values are appended; prior current rows are superseded without changing values or QC flags. Operational and spectral summaries use a separate audited helper and create no Result.

Batch derivation uses attempt.qcBatchId, then WorkItem.batchId, then null. An explicitly supplied differing batch refuses with RESULT_BATCH_MISMATCH; conflicting non-null server batches refuse with RESULT_BATCH_CONFLICT. Unbatched and historical import workflows remain available. Existing grouped-texture workbench attempts and offline attempts are created before their results and linked in the same transaction. General workbench attempt creation, numbering and repeat redesign remain with #190. Historical results are not back-filled.

Historical import follows scope pin https://github.com/yigini/soilfer-lims/issues/182#issuecomment-6005018712. Only the import controller may request its explicit historical option; the source inventory checks direct and aliased uses. Without a canonical WorkItem for the sample/parameter, historical imports keep their existing lifecycle exception and still validate permission, scope, catalogue/method/unit, parser and server batch. When a canonical item exists, including a waived item, the full sealed-work, prerequisite and fresh-calibration checks apply. Non-measurement scalar imports are refused. Existing results are superseded without overwriting their values.

The clarification in https://github.com/yigini/soilfer-lims/pull/246#issuecomment-6005783551 preserves historical cells that main accepted. The shared parser runs, but invalid text and out-of-range imported values retain their original text with `isValid=false`, parser flags and `IMPORTED_UNVALIDATED`. Non-numeric cells have null numericValue; valid cells in the same file still import. All permission, scope, catalogue/method/unit and existing-work readiness refusals remain.

External measurements use an allow-list. Result IDs, flags, rawInput and provenance cannot be supplied by the results API or workbench; batchId is comparison-only. Parser evidence and provenance are derived in the writer. Offline sync supplies only its generated receipt Result ID and existing payload flags via `syncResult`. `writeSpectralPrediction` sets the explicit internal prediction option and applies ordinary readiness/sealing rules. Typed inputs cannot claim PREDICTED provenance. The source inventory confines these internal options to their callers and confines derived readiness to the two texture functions; a generic writer's derived source refuses with RESULT_SOURCE_FORBIDDEN. There is no new prediction HTTP endpoint.

Offline grouped texture supersedes prior current non-numeric class rows under legacy analyses such as PSA in the same transaction as its new TEXTURE row. Numeric rows and historical values/flags remain unchanged, and receipt replay writes nothing.

Behaviour/deferred notes from the audit: selected equipment is checked for calibration even when equipment is optional. The measurement status API with a result payload now returns 409 RESULT_SUMMARY_NOT_ALLOWED. New refusal codes use the existing English-plus-code pattern; locale keys are deferred until a client displays them. Guards for WorkAttempt.workItemId and WorkItem.sampleId updates that could invalidate a result link belong to #190.

The migration adds only Result.attemptId, its index and three integrity triggers. It does not add a Prisma relation, rebuild tables, change old analytical/QC/audit rows or consolidate the pre-existing A94 review candidates. The installer checks the exact SHA256-bound release SQL, nullable column/index shape, trigger definitions and marker. Partial installations and forged/unmarked provenance refuse. A complete install is a zero-change no-op. Direct application startup checks the installation read-only before loading the app or schedulers.

After the current-head Claude audit pass, use the established release procedure: hold HTTP/WebSocket ingress, stop writers, retain a fresh DB/assets backup, and rehearse the actual candidate startup plus retained-image rollback on an owned backup copy. Then run the installer on the live DB while writers remain stopped:

```sh
node scripts/install_result_attempt_links.js --db /explicit/lab/dev.db --dry-run
node scripts/install_result_attempt_links.js --db /explicit/lab/dev.db --apply
node scripts/install_result_attempt_links.js --db /explicit/lab/dev.db --apply
```

Record the original-table checksums/schema/FKs/indexes/triggers, installer classification, marker SHA256, totalChanges, Result counts and backfillCount (zero). Repeat apply must report NO_OP/totalChanges 0. Check real app startup, role routes, scoped policies, database integrity and external health before restoring ingress. Preserve the backup and rollback image; recovery changes the image, never automatically restores or deletes analytical data.

SQLite WAL mount requirement (the #179 post-deploy follow-up): mount the DB directory read/write for the release's dry-run/startup probes so SQLite can manage WAL sidecars. Their SQL connections remain `readonly: true`; do not switch the installers' read-only inventory connections to writable connections. A read-only directory mount can refuse with SQLITE_CANTOPEN even when the DB itself exists. For an owned-copy probe use `-v "$owned_copy_dir:/app/server/prisma"`, without `:ro`. Compare the DB file hash and every original table before/after read-only probes to establish zero scientific-data changes. The normal application volume also requires sidecar access. Never probe the live database through a copied, stale WAL file.

The prior #179 migration/loader/frozen-deferral bytes remain unchanged. There is no new lab policy or inferred QC requirement. Scope pins for future policy requirements, general attempts, amendments and historical cleanup belong to their own issues.
