## 1. Overview for Laboratory Operators

SoilFER-LIMS is designed to run reliably in two primary operating modes:
1. **Single Laboratory (`local` mode):** Designed for an individual soil laboratory. Upon installation, it automatically provisions your laboratory record and an initial `LAB_MANAGER` administrator account. The manager can configure the lab, onboard technicians, register samples, and process analytical batches.
2. **Multiple Laboratories (`global` mode):** Designed for national agricultural institutes or laboratory networks coordinating several facilities. It provisions a central `SUPER_ADMIN` account who can create new laboratories, assign laboratory managers, and oversee cross-facility operations.

## 3. Installation & Getting Started Guides

### Prerequisites
- **Operating System:** Linux (Ubuntu 22.04 / 24.04 recommended), macOS, or Windows (WSL2).
- **Node.js:** Version 24 LTS is recommended (Node.js 20.19+ or 22.12+ supported).
- **Hardware:** Minimum 2 CPU cores, 2 GB RAM (3 GB recommended for Docker), 10 GB free disk space.
- **Port:** Port 3000 (standard web port) or Port 80/443 if using NGINX reverse proxy.

---

### Path A: Single-Laboratory Deployment (`local` mode)

*Use this path if you are setting up SoilFER-LIMS for a single laboratory facility.*

#### Step 1: Clone the Repository & Configure Environment
```bash
git clone https://github.com/yigini/soilfer-lims.git
cd soilfer-lims

# Copy sample configuration
cp .env.example .env
```

Open `.env` in a text editor:
```bash
# Required settings:
PORT=3000
NODE_ENV=production
DEPLOYMENT_MODE=local

# Security Secret: Leave blank to auto-generate on first boot, or generate now:
# node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
JWT_SECRET=
```

#### Step 2A: Quick Installation (Direct Node.js)
```bash
chmod +x setup.sh
./setup.sh local
```
The installer will:
1. Validate your Node.js runtime.
2. Install server and client production dependencies.
3. Build the React web application.
4. Generate the database schema and seed your laboratory.
5. Display your one-time initial admin password.

#### Step 2B: Docker Compose Installation
```bash
# Start container (runs in background)
docker compose up -d

# View initial admin credentials from startup logs:
docker compose logs lims | grep "INITIAL ADMIN CREDENTIALS" -A 4
```

#### Step 3: First Login & Mandatory Password Change
1. Open your browser and navigate to: `http://<your-server-ip>:3000` (or your domain).
2. Log in with:
   - **Username:** `admin`
   - **Password:** `<The initial password printed in Step 2>`
3. **Mandatory Security Step:** The system will immediately require you to choose a new strong password before granting access.
4. **Next Steps:** As `LAB_MANAGER`, go to **Settings** to update your laboratory name, address, and accreditation details, then go to **Staff** to invite technicians.

---

### Path B: Multi-Laboratory Network Deployment (`global` mode)

*Use this path if you are a national coordinator or institute managing multiple laboratories.*

#### Step 1: Configure Environment for Global Mode
In your `.env` file:
```bash
PORT=3000
NODE_ENV=production
DEPLOYMENT_MODE=global
JWT_SECRET=
```

#### Step 2: Launch the System
```bash
# Direct Node.js:
./setup.sh global

# Or via Docker Compose:
docker compose up -d
```

#### Step 3: First Login as System Administrator
1. Open: `http://<your-server-ip>:3000`
2. Log in with:
   - **Username:** `admin` (Role: `SUPER_ADMIN`)
   - **Password:** `<The initial password generated in Step 2>`
3. Change your password upon prompt.
4. **Provision Laboratories:**
   - Navigate to **Admin → Laboratories**.
   - Click **Add Laboratory** to configure each participating facility (name, code, country).
   - Create a `LAB_MANAGER` account for each laboratory.
   - Each manager can then log into their own laboratory workspace in complete isolation.

---

### Single-Lab Authority & API Ownership Boundary
In single-lab (`local`) mode:
- The seeded administrator has role `LAB_MANAGER`.
- For safety and data integrity, `LAB_MANAGER` is scoped strictly to laboratory operations (samples, methods, QA, reporting) and **cannot manage external data exchange API connections or system-wide credentials**.
- If external automated API integrations (such as OpenNSIS or Kobo sync) are required, the laboratory operator must create or elevate a designated `SUPER_ADMIN` system administrator account to configure API connections.

## 4. Upgrade, Backup, and Disaster Recovery Procedures

### Standard Upgrade Procedure
1. **Stop Writes & Take Backup:**
   ```bash
   cd /path/to/soilfer-lims
   docker compose stop lims
   
   # Backup SQLite database, WAL file, and uploads directory
   TIMESTAMP=$(date +%Y%m%d_%H%M%S)
   docker run --rm -v soilfer-lims_lims-data:/data -v $(pwd)/backups:/backup alpine \
     tar -czf /backup/db_backup_${TIMESTAMP}.tar.gz -C /data .
   docker run --rm -v soilfer-lims_lims-assets:/assets -v $(pwd)/backups:/backup alpine \
     tar -czf /backup/assets_backup_${TIMESTAMP}.tar.gz -C /assets .
   ```
2. **Fetch New Code & Build Updated Container:**
   ```bash
   git pull origin main
   docker compose build lims
   ```
3. **Start Upgraded Service:**
   ```bash
   docker compose up -d
   
   # Verify healthcheck passes:
   curl -f http://localhost:3000/api/health
   ```
   *Note: Additive database migrations are applied automatically and idempotently during container boot.*

### Disaster Recovery / Database Restoration
If restoring from a backup archive:
1. Ensure the application container is **stopped** (`docker compose stop lims`).
2. Restore database files into the designated volume (`soilfer-lims_lims-data`).
3. Verify SQLite integrity:
   ```bash
   sqlite3 dev.db "PRAGMA integrity_check;"
   sqlite3 dev.db "PRAGMA foreign_key_check;"
   ```
4. **Rotate Data Exchange Epoch:** If using automated external sync, advance the NSIS exchange epoch to prevent client synchronization conflicts (see `docs/nsis-operator-runbook.md`).
5. Restart the application: `docker compose up -d`.
